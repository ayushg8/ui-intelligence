# ai-product

**Evaluated:** 2026-09 · **Density:** comfortable · **Dark by default:** either, and the decision follows what the surface sits next to, not the archetype. General assistants ship light-first with dark parity (ChatGPT, Claude, Perplexity all default light — the artifact is prose and prose is read on paper-coloured ground). Coding and agent surfaces ship dark-first because they dock beside an editor and a light panel next to a dark editor is a flashlight. Either way the streamed prose must clear **7:1**, not 4.5:1: text that arrives one word at a time defeats the re-reading a reader normally uses to compensate for low contrast.

> A person types an under-specified request, waits an unpredictable and unbounded amount of time, and then has to decide whether to trust an artifact they did not watch being made.

## When this is the right archetype

A language model is the engine of the primary task, not a helper attached to it. Frequency is bimodal — a coding agent is used for six hours a day, a deck generator four times a quarter — so frequency does *not* set density here the way it does everywhere else in this corpus. Three structural conditions do, and all three must hold: **latency is unpredictable and unbounded** (the same prompt takes 2s or 4 minutes), **the output is non-deterministic** (the same input twice gives two different artifacts, so "undo" and "retry" are different operations), and **at least one action reaches outside the product** (sends, charges, writes, deploys). Every good decision below exists to compress the wait or to make the trust decision cheap.

- **Choose this over `technical-productivity` when** the user's input is a sentence rather than a selection. Both are keyboard-first; the difference is that Linear's user *triages a queue they can see* and this user *describes something that does not exist yet*. Diagnostic: if you can enumerate the valid next actions in a menu, you are in technical-productivity. If the composer must accept anything, you are here — and you owe streaming, disclosure and confirmation, none of which a queue product needs.
- **Choose this over `creative-tool` when** the only path to the artifact is a prompt and the canvas is a preview of what came back. If the user prompts once and then spends forty minutes nudging control points, `creative-tool` is the host and this file governs the generation pane only. This is the same boundary stated from the other side in [`creative-tool.md`](creative-tool.md); the two files must agree.
- **Choose this over `developer-platform` when** the surface is inference-time rather than integration-time. A model API's docs, keys, playground and usage dashboard are `developer-platform`. The chat the playground contains is a guest pane governed by this file.
- **Choose this over `analytics-bi` when** the answer is prose with provenance rather than a chart with a query behind it. A research agent that returns a cited table (Elicit) is still here, because the user cannot inspect the query that produced the row — they can only inspect the citation.

## When it is the wrong one

**A product that has an AI feature.** This is the failure vector, not an edge case. A bank, a CRM, a docs tool with an assistant is `fintech-institutional` / `enterprise-dense` / `editorial` **hosting** this archetype in one pane. The host owns density, type scale, neutrals and motion; this file owns the pane and nothing outside it. An assistant that makes the account list playful has failed at the archetype level before any component was written.

**Deterministic transformation.** Background removal, transcription, OCR, translation, a resume parser. A model is the implementation; the user situation is a file, a queue and a result. There is no under-specification, no unbounded wait, and nothing to confirm. That is a form with a job list, and giving it a composer, a streaming caret and a tool-call log is theatre that makes a 4-second job feel like a 4-minute one.

**A known option space with an easy mapping.** A filter that grew a natural-language box. If the user can see the options and the options are few, the prompt is a slower menu. The exception worth knowing: chat *is* right when translating the user's words into your taxonomy is the hard part — a claimant does not know that "water coming up through the slab" is a covered peril — but then the output of the mapping must be shown as the chosen option for confirmation, not answered in prose.

**Anything where a wrong answer is asymmetrically expensive at the moment of commit** — dosing, a wire, a filing deadline. Chat collects the intent; a form commits it. The archetype is right for the first half and catastrophic for the second, and products that let the conversation *be* the commit are the ones that end up in regulatory writeups.

**Sub-second inference the user never sees.** Autocomplete, ranking, spam classification, semantic search. No composer, no disclosure, no chrome. Showing `Called embed_query()` builds zero trust and costs a row.

## Colour

**The neutral ramp is achromatic and ten-to-twelve steps.** v0's is literally `hsl(0, 0%, …)` — zero saturation across all ten steps; ChatGPT's OKLCH ramp has chroma 0 at every stop. The reason is specific to this archetype: the transcript is a container for *other people's colour* — syntax highlighting, diff green and red, chart output, generated images, favicons in citation pills — and a blue-tinted grey behind all of it shifts every one. Perplexity is the deliberate exception and it is instructive about how to be warm without being tinted: a `#FDFBFA` ground with `#27251E` ink, and **muted text is the same ink at 65% opacity**, not a second grey, so there is exactly one hue in the whole neutral system.

**Colour's job here is unusual: it must report the state of a process the user cannot see.** That makes the semantic budget larger than in most archetypes and the decorative budget approximately zero. Six states need to be distinguishable in a transcript that also contains syntax highlighting.

The rule that makes it work, measured on AI Elements: **the status pill's body is neutral (`#F5F5F5`, 22px, 12/16 w500, 2px 8px, radius full) and only its 12px icon carries the state colour.** Amber clock = waiting on you. Red ⊗ = it threw. Green check = done. Blue check-circle = you answered. Grey = pending or denied. Six pills in six fills is a fruit salad; six identical chips with one coloured glyph reads as one system, and it satisfies the never-colour-alone requirement for free because every pill also carries its word. The inline citation pill (`example.com +5`) uses **the identical chrome** — same 22px, same 12/16 w500, same 2px 8px, same neutral fill. One chip primitive, two jobs.

**The accent is allowed four things:** the primary action, the focus ring, the user's own message tint, and citation/link colour. It is not allowed the assistant's output, section headers, icons generally, or any surface. **Only the user's message gets a bubble.** ChatGPT and Claude Code both render the human turn as a tinted container and the model's turn as unbubbled prose on the page ground — not a style choice: the assistant's output contains headings, code blocks, tables and citations, and a bubble is a container fighting its own contents.

**Disabled is a filled grey, never an opacity.** ChatGPT's `--button-primary-background-color-disabled` is `oklch(75.4% 0 none)` — a solid fill; t3.chat's disabled send is a filled tint. `disabled:opacity-50` on a shadowed composer drags the shadow and the border down with the button and reads as broken rather than as not-yet.

**Never a violet-to-blue gradient, a glowing orb, or a `✨`.** In 2026 that combination is the single fastest tell that nobody made a design decision, and it is doing the job that a specific capability sentence should be doing.

## Type

**Face:** a neutral grotesque whose most important property is its *monospace pair*, because 5–20% of the body text in this archetype is identifiers, paths and payloads. ChatGPT ships `ui-monospace` at `13/18` with a weight-500 emphasis variant; Vercel pairs Geist with Geist Mono; t3.chat pairs ProximaVara with BerkeleyMono. Pick the sans and the mono together and check them at the same optical size before you commit.

**Scale shape: two humps with a hole in the middle.** 12 / 13 / 14 for the metadata lane, 16 / 17 for prose — and then nothing at all until a single 24–32px empty-state heading that appears on one screen and never returns. This is the opposite of `editorial`'s continuous ramp and the reason is structural: the model supplies its own h1/h2/h3 inside the answer as markdown, so a chrome heading at 20px sitting next to a generated heading at 20px produces two hierarchies competing for the same meaning. Leave the middle of the scale to the model.

**Weights: 400 / 500 / 600.** The whole metadata lane is 500 at 12–14px — measured on every AI Elements primitive without exception. Weight is what buys legibility at 12px; a size bump would buy the same legibility by taking a column from the answer.

**Numerals:** `tabular-nums` on elapsed counters, token and context counts, diffstats, cost and durations. An elapsed timer that is not tabular jitters once a second for the entire length of a four-minute run — the most visible typographic defect in the archetype. t3.chat renders its cost indicator at `10px/13.33, ls −0.25px` in mono tabular.

**Monospace earns its place in five positions:** inline identifiers (as a **chip with a tinted background**, not a bare font swap — `createCharge()` inside 17px prose is unreadable as a naked font change), code blocks, diffs, file paths, and any payload rendered inside a confirmation. Drop one step when you switch: monospace at the same nominal size reads a full step larger. It does **not** earn its place on tool names — AI Elements renders `database_query` in **Geist sans, 14/20, weight 500**, measured, and that is right: the tool name is a label the user reads as English, not a token they will retype. (The corpus previously described this as monospace; the live component is sans.)

## Layout and navigation

There are three shells and the choice is set by where the output belongs, not by what the product does.

**(a) Rail + centred column + pinned composer** — general assistants. A 260px thread rail is the *entire* navigation; there is no top bar, because the only thing a top bar could carry is the current thread's identity and that belongs in a breadcrumb above the transcript where the eye already is.

**(b) Rail + transcript + artifact pane at 40/60** — whenever the output is iterated. Score it rather than guessing: iterated (+2), referenced while typing the next message (+2), exceeds one viewport (+1), has its own actions (+1), has versions (+1); three or more → panel. The two weighted criteria are weighted deliberately — length alone has never justified a pane, and "referenced while typing" is the real question, because it is asking whether the output needs **co-visibility with the composer**. Chat is the controller; the panel is the object; selection in the panel becomes a visible context chip in the composer, or users will paste code into chat to talk about code already on screen.

**(c) No shell — the AI is inside the object.** Granola puts the working state as a pill in the note body and the output in the note. Linear makes the agent an assignee, so it inherits the issue, the status transitions, the activity feed, the inbox and the mobile review flow. This is the correct shell whenever the user already has an artifact, and it is the one that the drawer is a failed attempt at.

**The primary object is the composer, not the transcript.** It is the only element with real elevation, the only one with a large radius, and the only one whose chrome is allocated before its contents exist. Everything else in the window is flat. The empty state is a fourth layout in which the composer is **vertically centred** with four or fewer elements around it; it drops to the bottom only once there is a conversation to sit above it.

**Grouping is by turn, then by lane, in a fixed order:** user message → context attribution → reasoning → tool rows → prose → action row. Same order every turn, so a user scanning a long transcript can find the tool log by position. The context attribution is its own dimmed line before any work starts — Linear's `⚓ API launch  added to context` — and it is the cheapest correction opportunity in the entire flow.

**Cards: for the artifact, the pending-action table and the template gallery. Never for a message.** A card per message adds two borders every 40px down a 4,000px scroll and doubles the transcript's visual weight to convey a boundary that whitespace already conveys.

## Components

**Belongs here:** a reserved-frame composer whose toolbar space is allocated before any control renders; a send affordance that is a **verb when the output is a durable artifact** (`Build now`, `Create`, `Ask`) and an arrow or a literal `↵` glyph when it continues a conversation; a stop button that replaces send in the same slot at the same size; a visible, reorderable queue above the composer; the seven-state tool row with a load-bearing collapsed summary; reasoning that auto-opens while it streams and auto-collapses when the answer starts; an inline citation pill sharing the status pill's chrome; a confirmation rendered as an inline **state of the specific tool call** with the literal payload expanded; a checkpoint whose restore reverts the workspace and never the log; a branch pager `‹ 2/3 ›` on the message that forked; an artifact header carrying relative freshness (`Updated 1 minute ago`), a version control and its own `Regenerate`; a shimmer on a sentence that names the work; a sessions list whose rows carry elapsed time and a diffstat; a context ring that appears only past ~50%.

**Does not belong here:** a `✨` entry point or an "AI Assistant" panel (use the affordance the user already uses for the analogous human act — `/` in a document, `@mention` in a tracker, the selection toolbar on text); a model dropdown of eleven version strings as the first thing on screen (name the intent — `Auto`, `Fast`, `Extra high` — and keep the raw list one level down); a bubble or card on the assistant's turn; a paper-plane icon; three bouncing dots; a percentage you cannot compute from a known plan; a confidence score (a model's self-reported certainty is uncalibrated, and rendering it launders a guess into a measurement); a `Sources:` heading at the bottom with no inline anchors; `AI can make mistakes` under every message; a toast for anything at all; raw tool JSON expanded by default; `aria-live` on the streaming region (mark the container `aria-busy` and announce once on completion); hover-only message actions; a temperature slider in settings.

## States in this archetype

**Empty is the most consequential screen in the product**, because a bad first prompt produces a bad first answer and the user concludes the model is bad. Four elements or fewer, composer vertically centred. **Two tiers beat one flat list** — four categories × four examples covers sixteen intents in the vertical space of eight rows. Generative products need *more* scaffolding than assistants, because the user genuinely does not know the input language: v0 ships four artifact-shaped chips **plus a reroll button**, converting a dead end into a second draw, then a template gallery whose cards carry real usage counts, because a chip *asserts* the product can do a thing and a template with 14.4K uses *proves* it. State the capability boundary here and nowhere else: `I can read this repo, run tests, and open a PR. I can't deploy.`

**Loading is four different design problems separated by duration, not one.** Under 1s: nothing. 1–10s: a shimmer on a real sentence that names the work — and **no noun, no shimmer**, because a bare LLM call with no tools and no retrieval has nothing honest to put there and a shimmering `Thinking…` is animated theatre; show a caret and, past ~5s, an elapsed count. 10–60s: a step list with the current step highlighted and a stop. 1–5 min: a step counter, per-step durations and the artifact so far. Past 5 min: the ability to leave — a notification, a durable entry in a sessions list, and a resumable URL.

**Error is three separate designs and merging them is the characteristic mistake.** (1) A **refusal is an answer** — same bubble, same typography, no red, no icon, no alert box, and no thumbs-up row underneath it. Wrapping a refusal in error chrome tells the user the product broke, so they retry, which burns quota and reproduces the refusal. (2) A **failed tool call stays inside its own card** as an Error pill on the same 22px chrome as Completed, with the detail behind the chevron, and the turn continues; lifting it to a page-level toast severs the causal link between the step and its failure. (3) **Failure after the user said yes** is its own taxonomy and it is the half nobody builds — auth expired between approval and execution, card declined, grant revoked mid-run, a 429 arriving at token 400, two of four emails sent, a payload that went stale while the approval sat. Each names a different next action, and collapsing any of them into a generic error destroys the most important fact in the transcript: that the user consented.

**Too much** is solved by internal scroll plus grouping, never by pagination. Eight consecutive reads become `Read 8 files ⌄`. A 40KB tool result gets a 200px box and a `Show all`. Silent truncation is the root cause of the entire "the AI ignored my file" complaint class — say it in the row: `Read 1.2MB · truncated to first 200 lines`.

**Rate-limited is content, not an interruption.** Perplexity's logged-out limit renders a complete assistant turn — summary line, body, and the *full* action row a real answer would get — whose body is the imperative `Sign up and repeat your request.` The wall itself goes in the composer, disabling send, with an **absolute local reset time** (`Resets at 3:00 PM`, never `try again in 47 minutes`) and the user's typed text preserved. If a cheaper model exists, offer it inline; that one string converts more dead ends than anything else in the failure taxonomy.

**Stopped keeps the work.** Mark the partial `Stopped`, offer `Continue` — not `Regenerate`, which throws away 400 good tokens to buy a different answer.

## Motion budget

**May animate:** the per-word stream reveal at **150ms** `fadeIn` — or `blurIn` for fast models, because the blur masks batch arrival better than pure opacity — with the animation wrappers **removed from the DOM entirely** when the stream ends; the reasoning disclosure opening and closing; a shimmer sweep at ~2s; the artifact panel entering at 180–260ms; a caret at 1Hz or slower.

**Must not animate:** a message entering the transcript; a tool row changing state; hover on any transcript row (colour only, 150ms, no transform, no lift — t3.chat's entire transition declaration is two colour properties); text at character granularity, which is a typewriter gimmick that triples DOM churn; a spinner that outlives the first token; and anything at all when `prefers-reduced-motion` is set, where the shimmer becomes a static dimmed label and the caret becomes solid.

**The frequency argument here is different from every other archetype's, and stronger.** Elsewhere the count is set by how often the user acts. Here it is set by how much the model wrote. A 4,000-word answer is 4,000 mount animations the user did not ask for, and if the wrappers survive completion, they stay in the DOM and every subsequent scroll of that thread pays for them. That is why the rule is *animate on mount, then delete the plugin from the pipeline* rather than *animate on mount*. On mobile, cut the reveal entirely: 600 animating spans on a mid-tier Android is a measurable battery cost for an effect nobody asked for.

## Mobile

Not a reduced product — a **reordered** one. The write step belongs on desktop; the phone's best case is the **review** step, and the products that understand this ship the strongest mobile experiences in the category (Linear ships per-line comments on an agent's returned diff on mobile, because reviewing a diff is exactly the thing you do from a phone while the writing happens in the cloud).

At 390 the composer is the whole design, and the control budget is **model chip + one `+` + send**. Never wrap the toolbar to a second row; when a control cannot survive the collapse, **promote it out of the composer rather than burying it** — t3.chat moves its mode switcher into a centred `Chat ⌄` pill in the top bar while folding Instant / Search / Attach into a leading `+`. Keep the affordance the control is *for* over the string that names it: t3 drops the version string and keeps the green cost glyph (`Kimi K2 $$·`); v0 drops the model label and keeps the provider mark. Put the `+` on the **leading** side, at the thumb's inner reach, so a mis-tap does not cost an accidental send.

The rest, in order of how often it is got wrong: `dvh`/`svh` plus `interactive-widget=resizes-content`, never `100vh`; **Enter inserts a newline and a button sends**; the empty-state composer is vertically centred with both suggestion tiers dropped, so the pre-keyboard and post-keyboard layouts are a short transition apart; citation pills open a **bottom sheet**, never navigate, with a ≥44px target under a smaller visual; approve/reject are ≥48px, full-width, stacked with the destructive option **on top** and ≥16px of gap, and never where send was one frame earlier; the artifact is a sheet from which the composer is still reachable, not a route the user must dismiss — dismissing loses their place; a completion notification carries the outcome (`Opened PR #482 · 12 files changed`), and an *approval* notification offers reject and open, never approve, because approving from a notification is approving something you did not read.

## Copy register

Past tense for what happened, imperative for what to do next, a number in every summary line, and no first-person self-narration — the model is not a character.

- `Read 3 files, searched the checkout flow ›` — beats `🔧 Tool: read_file` and beats `Analyzing your request…`. The count is what makes the line checkable.
- `Worked for 4m 13s  +25 −131` — beats `Generating response…`. At four minutes the user is in another tab; what they need on return is a receipt, not a status.
- `You've hit your Opus limit. Resets at 3:00 PM. [Continue with Sonnet]` — beats `Error 429. Please try again later.` An absolute time needs no arithmetic and no re-reading.
- `Send this invoice for $1,240.00 to alex@acme.com?` with buttons `Send invoice` / `Don't send` — beats `Are you sure?` with `Confirm` / `Cancel`. **A confirmation button is labelled with the action it performs**, so a user who reads only the buttons still chooses correctly.
- `Card declined — insufficient funds. $1,240.00 was not charged. [Try another card]` — beats `Payment failed`. The decline code implies a different user action every time, and stating what was *not* charged is what stops a dispute over the authorization hold.
- `Describe a task or ask a question` (Claude Code) — beats `Ask me anything`. It names both modes the surface actually supports.

Two rules underneath all of them. **Name the unit of work in the user's noun** — *session*, *task*, *plan*, *coding session*; never "agent invocation". And **put uncertainty in the specific answer, never in a persistent banner**: a banner that always says AI can make mistakes is read exactly once and is furniture by the third message, while a sentence naming which part is unverified is read every time.

## The characteristic failure

There are two bad versions and they fail differently. The **bolted-on** one is a product problem; the **imitated** one is a craft problem. Most shipped AI features are the first.

1. **The drawer.** A `✨` in the toolbar opens a 400px right panel containing a message list, a textarea, and the greeting `Hi! I'm your AI assistant. How can I help you today?` — with no idea what page the user is on. Output arrives as text with a Copy button that the user pastes back into the document by hand. Two questions separate native from bolted-on: **can the AI act on the thing the user is looking at, and does its output land where the user's own work lives?** Two nos is a drawer, and the fix is never a nicer drawer — it is an entry point in the affordance the user already uses for the analogous human act.
2. **Markdown that flickers.** No incomplete-block handling, so every `**` that arrives without its partner un-bolds the preceding phrase for a frame, every open fence renders as literal backticks for 200ms, and every half-arrived link shows raw brackets. This is the most damaging streaming bug because it happens on *every single message*.
3. **The dead wait.** Send → spinner → twelve seconds of nothing → a wall of text. The good products fill that window with something falsifiable; the bad one fills it with a fake progress bar that sits at 90%.
4. **Raw tool JSON, expanded, one card per call**, so a ten-tool turn is ten screens of `{"query": "..."}` before a sentence of answer. That is a debugger pasted into a product.
5. **Confirmation as a `confirm()`** reading "Are you sure you want to proceed?" with no payload — or a modal saying "The AI wants to perform an action", with `Approve` as the blue primary on a delete and an `Always allow` checkbox granting a scope the dialog never rendered. Worth knowing that AI Elements' own demo has exactly this defect, measured: on a file deletion, `Approve` is a filled `#0070F7` and `Reject` is a white outline. Copy its state machine; do not copy its button weighting. The rule to invert: **the less you can show, the less you may grant.**
6. **Post-approval failure collapsed into `Something went wrong`**, which erases the fact that the user consented and makes the next approval harder to get. Every one of them destroyed costs you the next one.
7. **Seven states rendered as two.** Losing `Awaiting Approval` puts the thing blocking the entire run behind a chevron. Losing `Denied` means a user cannot verify their own refusal held.
8. **Autoscroll pinned to the bottom**, so the reader chases text downward and never reads the opening paragraph — the single most-observed usability failure in published chatbot studies.
9. **A model picker of eleven version strings above an empty composer**, asking the user to make a choice they have no basis for before they have typed a word.
10. **`AI can make mistakes.` in 11px grey under every message**, doing the job that a per-claim citation was supposed to do — plus, in the worst version, a confidence percentage next to it.
11. **The imitation tell-stack:** bubbles on both sides, a card per message, 44px twitchy rows, `hover:shadow-md hover:-translate-y-0.5`, `disabled:opacity-50`, `rounded-lg` everywhere, and a violet-to-blue gradient on the send button. The real ones do not look like that — v0's send button is a 28×28 near-black square at r6, and its composer's outline is a `0 0 0 1px #00000014` shadow ring.
12. **Regenerate as the only recovery.** No edit, no branch, no continue — so every correction costs a full re-run and destroys the previous attempt.

**The ninety-second self-diagnostic.** Without reading any code: stream a message containing an unclosed ` ``` ` — does it render as a code block the whole time, or as literal backticks that snap? Scroll up mid-stream — does the view stop following and offer a pill? Inspect a finished 3,000-word message — how many animation spans are still in the DOM (the answer is zero)? Press Enter while a four-minute run is going — does it queue, interrupt, or no-op? Stop a stream — is the partial still on screen with a `Continue`? Find an approval for a real side effect — does it show the literal recipient, SQL or amount, and is the affirmative button labelled with the verb? Deny a tool call and scroll back an hour — is the denial still in the transcript? Kill the network at token 400 — is the partial preserved with a retry, or replaced by a red box? Eight questions. Three failures and it is not this archetype, however much it looks like one.

## Signature decisions that fit here

Pick exactly one, and it must come from the domain.

- **Every collapsed line in the transcript carries a count and a delta** — `Read 3 files, searched the checkout flow`, `Worked for 4m 13s +25 −131`, `Scanning 52 files → Scanning 2 files` — so the transcript is a scannable ledger rather than a log. Derived from the fact that at four minutes the user is not watching; what they need on return is what changed and how much, in one saccade.
- **Cost is a three-tier glyph inline in the model chip** (`Kimi K2 $$·`), not a token count and not a dollar figure, and it is the one part of the chip that survives the 390px collapse. In a product where the user picks a model per message, the recurring question is "is this the expensive one", and a number requires arithmetic the user will not do.
- **The confirmation renders the payload in the payload's own shape** — an email as From / To / Subject / body, a database write as the SQL, a purchase as the line item and the last four — and the "don't ask again" option appears **only when the prompt can display everything that option would allow**. A command too long to render gets a one-time approval and no standing grant.
- **Rejection carries a reason in the same interaction**, and a reasoned rejection lets the agent keep working while a bare one stops the turn. That asymmetry turns the permission prompt from a gate into a steering wheel: the cheapest path back into flow is to say why you refused.
- **Restoring a checkpoint reverts the workspace and never the conversation.** The log is append-only; the world is mutable. The user keeps the record of the mistake they were trying to learn from, which is the thing a full undo silently destroys.
